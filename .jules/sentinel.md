## 2025-02-24 - [Fix Reflected User Input in InvalidUuid Error]
**Vulnerability:** The application was reflecting untrusted, unsanitized user input (the invalid UUID string) directly in the `400 Bad Request` HTTP error response.
**Learning:** Returning unvalidated input directly in error messages can lead to Reflected XSS (if rendered by a client) or log forging. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting.
**Prevention:** Avoid allocating and reflecting raw user input in error enum variants like `InvalidUuid(String)`. Use static error messages like `InvalidUuid` for malformed input unless specific, sanitized context is required and safe to expose.

## 2025-02-26 - [Fix Reflected User Input in InvalidUuid and Unique Violation Errors]
**Vulnerability:** The application was catching unique constraint violations but exposing the raw database errors via generic 500 status responses (which can expose database schema details, constraints, and potentially user inputs in a reflected XSS attack if rendered) when `fetch_one` or `execute` methods failed with unique constraint violations.
**Learning:** Returning unvalidated or raw database errors directly in error messages can lead to log forging, information leakage, and potentially Reflected XSS. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting and not leak raw sqlx errors.
**Prevention:** Avoid exposing raw database errors. Use `.map_err` to explicitly map `e.as_database_error().map(|db| db.is_unique_violation())` to specific, safe domain errors like `DbError::UniqueViolation("Static error message".to_string())` for malformed input and constraint violations.
