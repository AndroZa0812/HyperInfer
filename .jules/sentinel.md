## 2025-02-24 - [Fix Reflected User Input in InvalidUuid Error]
**Vulnerability:** The application was reflecting untrusted, unsanitized user input (the invalid UUID string) directly in the `400 Bad Request` HTTP error response.
**Learning:** Returning unvalidated input directly in error messages can lead to Reflected XSS (if rendered by a client) or log forging. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting.
**Prevention:** Avoid allocating and reflecting raw user input in error enum variants like `InvalidUuid(String)`. Use static error messages like `InvalidUuid` for malformed input unless specific, sanitized context is required and safe to expose.

## 2025-02-26 - [Fix Error Message Masking (Security Information Leakage)]
**Vulnerability:** The application was formatting the raw `sqlx::Error` inside the `DbError::Sqlx` display implementation (via `thiserror`), meaning that database-level errors (including internal table names, schemas, SQL query syntax, and connection string variables) could bubble up to public-facing HTTP 500 error responses and application logs.
**Learning:** Using `#[error("Database error: {0}")]` on a `sqlx::Error` propagates internal server state directly to callers. Even generic endpoints might leak the underlying structure or query strings upon failing constraints, connection failures, or bad syntax.
**Prevention:** Mask raw internal infrastructure errors before returning them. Change `#[error("Database error: {0}")]` to `#[error("Database error")]`. The underlying source error is still preserved in Rust via `source()` for local structured logging or stack traces, but the `.to_string()` output will not leak specifics to external consumers.
