## 2025-02-24 - [Fix Reflected User Input in InvalidUuid Error]
**Vulnerability:** The application was reflecting untrusted, unsanitized user input (the invalid UUID string) directly in the `400 Bad Request` HTTP error response.
**Learning:** Returning unvalidated input directly in error messages can lead to Reflected XSS (if rendered by a client) or log forging. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting.
**Prevention:** Avoid allocating and reflecting raw user input in error enum variants like `InvalidUuid(String)`. Use static error messages like `InvalidUuid` for malformed input unless specific, sanitized context is required and safe to expose.

## 2025-02-26 - [Fix Sensitive Data Exposure in Error Display]
**Vulnerability:** The `thiserror` `#[error(...)]` macros for `DbError::Sqlx` and `ConfigError::Redis` were formatting the raw underlying errors (`sqlx::Error` and `redis::RedisError`) into their `Display` strings using the `{0}` placeholder.
**Learning:** Returning unvalidated input directly in error messages can lead to sensitive information disclosure. For infrastructure errors like database and Redis connection issues, the raw error message might contain sensitive details like connection strings, usernames, passwords, internal hostnames, or specific SQL queries and schema information. Exposing these details to a user or client via a web response could provide an attacker with valuable information about the backend infrastructure.
**Prevention:** Avoid formatting raw, underlying infrastructure errors directly into the `Display` implementation of application-level errors. Instead, use generic static error strings (e.g., `"Database error"`, `"Redis error"`) in the `#[error(...)]` macro, omitting the `{0}` placeholder. The underlying error will still be preserved and accessible for internal logging or debugging via the `Debug` format (`{:?}`) or the `std::error::Error::source()` method, without being exposed to end users.
