## 2025-02-24 - [Fix Reflected User Input in InvalidUuid Error]
**Vulnerability:** The application was reflecting untrusted, unsanitized user input (the invalid UUID string) directly in the `400 Bad Request` HTTP error response.
**Learning:** Returning unvalidated input directly in error messages can lead to Reflected XSS (if rendered by a client) or log forging. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting.
**Prevention:** Avoid allocating and reflecting raw user input in error enum variants like `InvalidUuid(String)`. Use static error messages like `InvalidUuid` for malformed input unless specific, sanitized context is required and safe to expose.

## 2025-03-02 - [SSRF Mitigation with Custom DNS Resolver]
**Vulnerability:** A Server-Side Request Forgery (SSRF) vulnerability existed because URL validation was performed via string matching against blocked IP prefixes prior to HTTP connection, rendering it susceptible to DNS rebinding attacks and alternative IP encodings.
**Learning:** Checking URL hosts against literal string lists before executing a request is fundamentally insufficient in asynchronous systems due to TOCTOU (Time-of-Check Time-of-Use) issues like DNS rebinding. Furthermore, using unstable Rust methods (`Ipv4Addr::is_documentation`) or failing to check standard IPv6 private addresses using stable bitwise operations breaks compilation or bypasses protection entirely.
**Prevention:** Always implement a custom `reqwest::dns::Resolve` trait to asynchronously evaluate the *resolved* IP addresses prior to connecting. When validating IPv6 addresses on stable Rust, manually parse the `octets()` to detect unique local and unicast link-local addresses since methods like `is_unique_local` are unstable. Also ensure to turn off transparent HTTP redirects (`reqwest::redirect::Policy::none()`) to prevent bypasses via 301/302 redirects to internal IPs.
