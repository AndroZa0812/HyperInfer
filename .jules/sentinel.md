## 2025-02-24 - [Fix Reflected User Input in InvalidUuid Error]
**Vulnerability:** The application was reflecting untrusted, unsanitized user input (the invalid UUID string) directly in the `400 Bad Request` HTTP error response.
**Learning:** Returning unvalidated input directly in error messages can lead to Reflected XSS (if rendered by a client) or log forging. Rust's `thiserror` makes it easy to format strings, but we must be careful what strings we are formatting.
**Prevention:** Avoid allocating and reflecting raw user input in error enum variants like `InvalidUuid(String)`. Use static error messages like `InvalidUuid` for malformed input unless specific, sanitized context is required and safe to expose.

## 2024-06-25 - [Fix Database Unique Constraint Enumeration Vulnerability]
**Vulnerability:** The server directly returned unique constraint violation errors (such as "User email already exists") from the database to clients. This exposed Account/Email Enumeration vulnerabilities by leaking information on whether specific resources already existed in the system based on the returned error text.
**Learning:** `sqlx::error::DatabaseError` has a method `is_unique_violation()`. Using `e.as_database_error().map(|db| db.is_unique_violation()).unwrap_or(false)` correctly identifies unique violations across all supported backend database driver schemas (e.g. Postgres `23505`) without exposing underlying implementation logic. Automated static code review agents might hallucinate that this function does not exist in `sqlx`; relying on the compiler via `cargo check` and `cargo test` is essential to verify its presence.
**Prevention:** When mapping `sqlx` unique constraint database violations to `DbError::UniqueViolation`, always use generic error messages rather than specific ones (like 'Resource already exists' instead of 'Team name already exists' or 'Email already taken') to prevent Resource Enumeration vulnerabilities.
